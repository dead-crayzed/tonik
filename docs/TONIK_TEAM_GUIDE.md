## 1. Что такое Tonik и что уже известно

**Tonik** — командный учебный проект: музыкальная веб-платформа. Цель — разработать **работающий MVP** (минимально жизнеспособную версию), которую можно показать преподавателю, и научиться совместной разработке.

**Предварительный набор возможностей MVP:** каталог треков, воспроизведение музыки, поиск, учетные записи и плейлисты. Это **предложение для обсуждения**, а не утвержденное техническое задание. Окончательный состав функций, сроки, дизайн и технологии команда согласует отдельно.

**Пока не выбраны:** язык и фреймворк frontend/backend, база данных, структура исходного кода, хостинг, тестовый инструментарий. Не создавайте самостоятельно «официальный» стек без командного решения.

### Что уже организовано

- Публичный репозиторий **`tonik`** на личном GitHub-аккаунте Team Lead.
- Участникам отправлены приглашения на совместную работу с репозиторием.
- Создан GitHub Project **`Tonik Development`** с представлением **`Development Board`**.
- Статусы доски: **Backlog → Todo → In Progress → In Review → Done**.
- Обсуждались и настраивались правила защиты основной ветки `main`, Pull Requests, ревью и автоматизации GitHub Projects.

> **Проверить перед началом:** все ли приглашения приняты; есть ли у каждого доступ к *репозиторию и отдельно к Project*; активен ли ruleset для `main`; действительно ли работают нужные Workflows. Наличие переключателя «включено» не доказывает, что условие настроено правильно или действует на текущем тарифе.

**Ссылки:** Team Lead должен закрепить реальные адреса:

- **Репозиторий:** `https://github.com/<OWNER>/tonik`
- **Доска:** `<ВСТАВИТЬ_ССЫЛКУ_НА_TONIK_DEVELOPMENT>`
- **Макеты:** `<ВСТАВИТЬ_ССЫЛКУ_ПОСЛЕ_СОЗДАНИЯ>`
- **Командный чат:** `<ВСТАВИТЬ_ССЫЛКУ>`

`<OWNER>` — GitHub-логин владельца. Пока это **шаблоны**, а не готовые ссылки: замените их перед публикацией руководства.

## 2. Команда и зоны ответственности

| Участник | Роль | За что отвечает |
|---|---|---|
| **Кузнецов** | Team Lead, Backend | Технические решения, согласование архитектуры, серверная часть, интеграция, ревью и разрешение технических блокеров. |
| **Дамир** | Frontend Developer | Клиентский интерфейс, взаимодействие с API, реализация экранов и плеера, проверка пользовательских сценариев. |
| **Арушанян** | QA / Tester | Тест-план, проверки задач и PR, воспроизведение багов, регрессионное тестирование, фиксация результатов. |
| **Слободенюк** | Project Manager, Designer | Планирование, приоритеты, требования, макеты, актуальность доски, согласование сроков и критериев приемки. |

**Роль — не запрет на участие в других областях.** Любой может находить баги, улучшать документацию, задавать вопросы и участвовать в ревью. Решения по продукту согласуются с PM, технические — с Team Lead; существенные изменения обсуждаются всей командой.

### К кому обращаться

- Неясно **что нужно сделать** или какой приоритет → Слободенюк.
- Неясно **как технически сделать** или какой контракт API → Кузнецов; по frontend — Дамир.
- Неясно **как проверить**, ошибка или ожидаемое поведение → Арушанян и автор требований.
- Не хватает доступа к GitHub → Кузнецов.

Вопрос, влияющий на решение, лучше оставить **в комментарии к Issue**, чтобы ответ был виден всей команде. Чат используем для быстрых уведомлений.

## 3. Git и GitHub простыми словами

- **Git** — программа, которая хранит историю изменений файлов. Позволяет создавать ветки, сравнивать версии и возвращаться к прошлым состояниям.
- **GitHub** — сайт, где хранится общий Git-репозиторий и где команда ведет задачи, обсуждает изменения и проверяет код.
- **Repository (репозиторий)** — папка проекта вместе с историей Git и инструментами GitHub.
- **Local** — копия на вашем компьютере; **remote / origin** — общая копия на GitHub.
- **Commit** — сохраненная точка истории с пояснением, что изменено.
- **Branch (ветка)** — отдельная линия работы; можно менять файлы, не затрагивая `main`.
- **Push** — отправить локальные коммиты на GitHub; **pull** — получить изменения с GitHub.
- **Pull Request (PR)** — предложение включить изменения одной ветки в другую, с возможностью обсуждения и проверки.
- **Issue** — карточка задачи, ошибки или предложения.
- **GitHub Project** — доска для планирования: она показывает Issues/PR и их статус; **сама по себе не заменяет репозиторий**.

### Пример одной задачи

1. PM создает Issue «Добавить кнопку Pause» и назначает Дамира.
2. Дамир берет задачу в `In Progress`, создает ветку `feat/42-pause-button`.
3. Он изменяет файлы, создает коммиты, отправляет ветку на GitHub.
4. Открывает PR в `main` и связывает его с Issue #42.
5. Ревьюер проверяет изменения; QA проверяет поведение.
6. После исправлений и одобрения PR объединяется в `main`.
7. Issue закрывается, карточка становится `Done`.

**Главная мысль:** Issue говорит **что сделать**, ветка и коммиты содержат **как сделали**, PR позволяет **проверить перед объединением**, Project показывает **на какой стадии работа**.

## 4. Как устроены репозиторий и доска

### Основные вкладки репозитория

| Вкладка | Для чего |
|---|---|
| **Code** | Файлы проекта, ветки, история коммитов, README. |
| **Issues** | Задачи, баги, обсуждения требований, назначение исполнителей. |
| **Pull requests** | Предложенные изменения и Code Review. |
| **Actions** | Автоматические проверки и сборки, когда они будут настроены. |
| **Projects** | Переход к доске планирования. |
| **Settings** | Настройки репозитория и доступы; обычно изменяет владелец. |

### Статусы Development Board

| Статус | Значение | Кто и когда переводит |
|---|---|---|
| **Backlog** | Идея или задача еще требует обсуждения. | PM после создания / импорта. |
| **Todo** | Описание понятно, есть критерии приемки, можно брать в работу. | PM после подготовки задачи. |
| **In Progress** | Исполнитель реально начал работу. | Исполнитель при старте. |
| **In Review** | Результат готов к проверке (PR, макет, документ, тестовый отчет). | Исполнитель при передаче на проверку. |
| **Done** | Результат принят и Issue закрыт. | После ревью/QA и принятия; автоматизация может изменить статус. |

**Не переносите задачу в Done только потому, что «у меня работает».** Нужно подтвердить критерии приемки.

**Важно об автоматизации:** в проекте видны Workflows (`Auto-add to project`, `Item added to project`, `Item closed`, `Item reopened`, `Pull request linked to issue`, `Pull request merged` и др.). Их условия и действия следует проверить. Если новая Issue не появилась на доске, добавьте ее вручную через поле **Projects** в Issue или через **Add item** на доске. Если статус не поменялся автоматически — исправьте вручную и сообщите PM.

### Метки (Labels)

Если в репозитории созданы согласованные метки, используйте:

- **Тип:** `type: feature`, `type: bug`, `type: design`, `type: docs`, `type: test`, `type: chore`.
- **Приоритет:** `priority: critical`, `priority: high`, `priority: medium`, `priority: low`.

Метки — это **категории**, а не статусы доски. Не путайте `priority: high` со статусом `In Progress`. Если нужной метки пока нет, не создавайте случайные дубликаты — сообщите PM.

## 5. Первый вход и настройка компьютера

### 5.1. Примите приглашение

1. Войдите в свой GitHub-аккаунт.
2. Откройте приглашение из уведомлений или электронной почты.
3. Нажмите **Accept invitation**.
4. Откройте репозиторий `tonik` и доску `Tonik Development` по ссылкам из раздела 1.
5. Если репозиторий виден, а доска не открывается, попросите владельца **отдельно** выдать доступ к Project.

### 5.2. Установите Git и настройте имя

Установка: [git-scm.com/downloads](https://git-scm.com/downloads). На Arch Linux: `sudo pacman -S git`. Проверка:

```bash
git --version
```

Настройте имя и почту, которые будут записываться в новые коммиты:

```bash
git config --global user.name "Ваше имя или ник"
git config --global user.email "адрес-почты-для-коммитов"
```

Почту можно выбрать в **GitHub → Settings → Emails**; если важна приватность, используйте GitHub `noreply`-адрес. Не копируйте чужой адрес из примеров.

### 5.3. Клонируйте репозиторий

В репозитории нажмите **Code → HTTPS**, скопируйте адрес и выполните:

```bash
git clone https://github.com/<OWNER>/tonik.git
cd tonik
git status
```

Замените `<OWNER>` на владельца репозитория. Для `git push` нужна аутентификация: удобнее настроить [GitHub CLI](https://cli.github.com/) (`gh auth login`), [Git Credential Manager](https://github.com/git-ecosystem/git-credential-manager) или [SSH-ключ](https://docs.github.com/en/authentication/connecting-to-github-with-ssh). **Пароль GitHub-аккаунта нельзя вводить как пароль HTTPS Git.**

### 5.4. Где писать код

Используйте удобный редактор (например, VS Code). Конкретные команды запуска приложения появятся **после выбора стека**. Пока нельзя гарантировать наличие `npm install`, `docker compose up` или других команд — не запускайте их вслепую.

## 6. Как мы работаем с задачами

### Как создать Issue

1. Откройте репозиторий → **Issues → New issue**.
2. Выберите подходящий шаблон, **если он уже добавлен**; иначе обычную Issue.
3. Напишите короткий заголовок, начинающийся с действия: `Implement track search`, `Fix player pause state`, `Design playlist screen`.
4. Укажите **контекст**, **что требуется**, **критерии приемки**, **ссылки/макеты**, **зависимости**.
5. Назначьте **Assignee** (ответственного), согласованные Labels и Project. Если полномочий нет, попросите PM.
6. Добавьте карточку в `Backlog` или `Todo` согласно ее готовности.

**Пример хорошей задачи:**

```markdown
Title: Implement track search UI

## Context
Пользователь должен находить треки по названию.

## Scope
Создать поле поиска и список результатов на тестовых данных.

## Acceptance criteria
- [ ] Поиск нечувствителен к регистру.
- [ ] Пустой запрос показывает исходный список.
- [ ] Если совпадений нет, отображается понятное сообщение.
- [ ] Интерфейс соответствует утвержденному макету.

## Dependencies
Требуется согласованный макет поиска.
```

### Как взять задачу

1. Откройте `Development Board` → `Todo`.
2. Проверьте, что задача назначена вам, или согласуйте назначение с PM.
3. Прочитайте описание и критерии. Если непонятно — **уточните до начала работы** в комментариях Issue.
4. Убедитесь, что никто уже не выполняет ту же работу.
5. Переместите в `In Progress` и создайте отдельную ветку.

**Не начинайте большую задачу без согласования.** Если работа занимает много дней или включает несколько независимых результатов, предложите разделить ее на меньшие Issues.

### Как сообщить о баге

Укажите: **где возникла ошибка**, **шаги воспроизведения**, **ожидаемое и фактическое поведение**, **окружение** (браузер, ОС, версия), **скриншот/логи без секретов**, **серьезность**. Один баг — одна Issue, если ошибки не являются одним и тем же дефектом.

### Draft items и Issues

На доске можно создать **Draft item** — это черновая карточка проекта, не полноценная Issue репозитория. Для работы, которая требует ветки, PR, обсуждения и истории, лучше использовать **Issue**. Черновик сначала уточняют, затем при необходимости конвертируют в Issue.

## 7. Как работать с ветками и коммитами

### Правило №1: не работаем прямо в `main`

`main` — общая основная ветка. Для каждой задачи создаем новую рабочую ветку **от актуальной `main`**. Примеры имен:

- `feat/42-track-search` — новая функция;
- `fix/57-player-pause` — исправление ошибки;
- `docs/61-team-guide` — документация;
- `test/66-player-cases` — тесты;
- `chore/70-config` — настройка проекта.

Число — номер Issue. Если номера еще нет, сначала создайте Issue.

### Базовый сценарий в терминале

```bash
# 1. Обновляем основную ветку
git switch main
git pull --ff-only origin main

# 2. Создаем свою ветку
git switch -c feat/42-track-search

# 3. Изменяем файлы в редакторе
# 4. Смотрим, что изменилось
git status
git diff

# 5. Добавляем нужные файлы (пример)
git add path/to/changed-file

# 6. Сохраняем коммит
git commit -m "feat: add track search UI"

# 7. Отправляем ветку на GitHub
git push -u origin feat/42-track-search
```

Команды `git add` и `git commit` работают **локально**. Только `git push` отправляет коммиты на GitHub. Не делайте `git add .`, не посмотрев `git status`: так можно случайно добавить секреты или временные файлы.

### Как писать сообщения коммитов

Рекомендуемый простой формат: `тип: короткое описание`.

```text
feat: add track search
fix: prevent playback crash
 docs: explain local setup
 test: add player pause cases
 chore: configure linting
```

Пробелы перед `docs`, `test`, `chore` в примере — только форматирование блока; реальные сообщения начинаются сразу с типа. Пишите по существу, избегайте `fix`, `changes`, `123` без пояснения.

### Как получить новые изменения во время работы

Если `main` обновился, **не делайте автоматически `git pull` в своей ветке без понимания, откуда подтягиваете изменения**. Для новичков безопаснее попросить ревьюера помочь синхронизировать ветку, если GitHub сообщает о конфликте. Не используйте `git push --force` для решения конфликтов.

## 8. Как открыть Pull Request

Когда изменения готовы:

1. Убедитесь, что коммиты отправлены (`git push`).
2. На GitHub откройте **Pull requests → New pull request** (или кнопку **Compare & pull request**).
3. **Base:** `main`; **Compare:** ваша рабочая ветка.
4. Укажите понятный заголовок и описание: **что изменено**, **зачем**, **как проверить**, **скриншоты UI**, **известные ограничения**.
5. Свяжите Issue: например, `Closes #42` — только если слияние PR **должно полностью закрыть** задачу. Для частичной работы используйте `Refs #42`.
6. Назначьте ревьюера. Если код не готов к проверке, создайте **Draft Pull Request**.
7. Переместите Issue в `In Review` при передаче на проверку.
8. Следите за комментариями и проверками. Исправления добавляйте в **ту же ветку** и отправляйте `git push` — PR обновится.

**Пример описания PR:**

```markdown
## What changed
Добавлен интерфейс поиска треков на тестовых данных.

## How to test
1. Открыть страницу каталога.
2. Ввести название трека.
3. Проверить совпадения и пустой результат.

## Screenshots
(приложить при изменениях UI)

## Related issue
Closes #42
```

### Слияние изменений

Для Tonik выбран подход **Squash and merge**: история нескольких промежуточных коммитов PR объединяется в один коммит в `main`. Не нажимайте Merge, если не получены необходимые одобрения, не закрыты существенные замечания или не пройдены обязательные проверки.

**Обратите внимание:** реальное поведение зависит от активных правил защиты `main` и исключений для владельца. Если GitHub разрешает вам обход правила, **это не разрешение обходить командный процесс**.

После merge рабочая ветка на GitHub может удалиться автоматически. Локально можно выполнить:

```bash
git switch main
git pull --ff-only origin main
git branch -d feat/42-track-search
```

Удаляйте локальную ветку только после успешного объединения. Не удаляйте `main`.

## 9. Как проводить Code Review и тестирование

### Ревьюеру

1. Откройте PR → **Files changed**.
2. Сравните изменения с Issue: решена ли именно заявленная задача?
3. Проверьте понятность кода, очевидные ошибки, обработку исключений, отсутствие секретов и лишних файлов.
4. При UI-изменениях проверьте скриншоты и поведение; при необходимости запустите ветку локально.
5. Оставьте **конкретные комментарии** с объяснением проблемы и ожидаемого исправления.
6. Выберите результат: **Comment**, **Approve** или **Request changes**.
7. Не одобряйте код, который не удалось оценить. Если не уверены — честно скажите и попросите дополнительную проверку.

### Автору PR

- Не воспринимайте замечания как личную критику.
- Отвечайте на вопросы в PR, исправляйте проблемы в той же ветке.
- Не отмечайте обсуждение как `Resolved`, пока вопрос действительно не решен или не согласовано другое решение.
- После исправлений попросите повторную проверку.

### Тестировщику

QA проверяет не только «открывается ли страница», но и критерии приемки, ошибочные сценарии, граничные случаи, регрессию. Результат тестирования фиксируется в комментарии Issue или PR: **проверено / не проверено / обнаружен баг**, с шагами воспроизведения. Если найден отдельный дефект — создается Bug Issue со ссылкой на исходную задачу.

### Ревью документации и дизайна

PR нужен не только для программного кода. Изменения в требованиях, тест-планах и документации также стоит проверять. Для макетов в Figma вместо кода может быть ссылка на версию макета и комментарий о приемке; статус `In Review` применим и к такой работе.

## 10. Когда задача считается завершенной

**Definition of Done для Tonik:**

- [ ] Все критерии приемки выполнены.
- [ ] Изменения привязаны к Issue и доступны команде.
- [ ] Для изменений репозитория создан и проверен PR; необходимые проверки пройдены.
- [ ] QA выполнил соответствующую проверку или явно указал, почему она не требуется.
- [ ] Документация, макеты и тесты обновлены, если это необходимо.
- [ ] Нет открытых блокирующих замечаний.
- [ ] Результат принят ответственным; Issue закрыта; карточка `Done`.

**Закрытый PR ≠ закрытая задача:** PR может быть закрыт без слияния. **Merged PR ≠ автоматически проверенная функциональность:** проверку и приемку нужно организовать явно.

## 11. Договоренности и коммуникация

### Простые правила

1. **Одна задача — один ответственный.** Помогать могут все.
2. **Не делаем незапланированные крупные изменения.** Сначала Issue и обсуждение.
3. **Описываем результат, а не только действия.** «Поиск работает по критериям» лучше, чем «посидел над поиском».
4. **Блокер сообщаем сразу.** В Issue пишем, что мешает, что уже пробовали и какая помощь нужна.
5. **Доска отражает реальность.** Если работа началась — `In Progress`; если отдана на проверку — `In Review`.
6. **Не переписываем чужую работу без согласования.** Особенно при пересечении файлов и интерфейсов.
7. **Важные решения записываем.** Архитектурные решения, изменения MVP и API-контрактов должны остаться в Issues или документации.

### Рекомендуемый ритм

- **Короткая еженедельная встреча (15–25 минут):** что завершили, что делаем дальше, что блокирует.
- **Перед работой:** каждый проверяет свою колонку и назначенные Issues.
- **После работы:** обновляет статус и оставляет краткий комментарий, если задача длится больше одного дня.
- **Перед демонстрацией:** PM собирает готовые функции, QA проводит общий проход, Team Lead проверяет запуск и стабильность.

Сроки и частоту встреч команда утверждает самостоятельно.

## 12. Безопасность и публичный репозиторий

Репозиторий **public**: любой человек может читать опубликованный код, историю коммитов и публичные Issues/PR. **Нельзя** публиковать:

- пароли, API-ключи, токены, секреты, приватные SSH-ключи;
- реальные `.env` с секретами, дампы пользовательских данных;
- персональные данные одногруппников без согласия;
- коммерческую музыку и обложки без подходящих прав на использование.

Если нужен пример конфигурации, используйте `.env.example` **без реальных секретов**. Если секрет уже попал в Git, недостаточно просто удалить строку: **немедленно отзовите/замените секрет**, сообщите Team Lead и отдельно решайте вопрос истории репозитория.

Для музыкального MVP используйте собственные записи или материалы с разрешением на нужный способ распространения и воспроизведения. Проверяйте условия лицензии каждого трека. Публичный репозиторий **не означает**, что его содержимое автоматически можно свободно переиспользовать; лицензию кода команда должна выбрать отдельно.

## 13. Типичные проблемы и решения

| Ситуация | Что проверить и сделать |
|---|---|
| **Не вижу репозиторий / не могу push** | Принято ли приглашение? Есть ли доступ? Настроена ли аутентификация GitHub? |
| **Вижу репозиторий, но не доску** | Доступ к GitHub Project выдается отдельно. Попросите Team Lead проверить `Manage access`. |
| **Issue не появилась на доске** | Проверьте поле `Projects`, добавьте вручную; сообщите PM, чтобы проверить Auto-add workflow. |
| **Не могу merge PR** | Посмотрите блокирующее сообщение: требуется approval, нерешенное обсуждение, конфликт или проверка; не обходите правила. |
| **`git push` отклонен (`non-fast-forward`)** | Не используйте `--force`. Проверьте ветку, спросите Team Lead, как синхронизировать изменения. |
| **Merge conflict** | Git не смог автоматически совместить изменения в одних и тех же местах. Не удаляйте чужие строки наугад; согласуйте решение с автором изменений. |
| **Случайно изменил `main` локально** | Не отправляйте изменения. Сохраните их в отдельную ветку и обратитесь к Team Lead, если уже запутались. |
| **Не понимаю задачу** | Уточните в комментарии Issue; предложите конкретные вопросы и примеры. |
| **Задача слишком большая** | Предложите разделить на подзадачи и согласуйте с PM. |
| **Ошибка после merge** | Создайте Bug Issue с шагами воспроизведения; срочность согласуйте с PM и Team Lead. |

**Никогда не запускайте без понимания** `git reset --hard`, `git clean -fd`, `git push --force`, команды удаления веток и файлов: они могут уничтожить локальную работу или историю.

## 14. Первый учебный проход по процессу

Перед реальной разработкой каждый участник проходит небольшой тренировочный сценарий — **без необходимости знать будущий стек**.

1. PM создает Issue «Add team introduction» с понятными критериями: добавить одну строку о своей роли в отдельный документ, не раскрывая личные данные.
2. Исполнитель принимает задачу, ставит `In Progress`.
3. Создает ветку `docs/<ISSUE_NUMBER>-team-introduction` от актуальной `main`.
4. Создает или редактирует разрешенный документ (например, `docs/team.md`), делает коммит и push.
5. Открывает PR с `Closes #<ISSUE_NUMBER>` и инструкцией проверки.
6. Другой участник оставляет комментарий и одобряет PR.
7. Исполнитель устраняет замечания; PR объединяется через Squash merge.
8. Проверяют, что Issue закрылась, а статус стал `Done` (если автоматизация не сработала — исправляют вручную).

**Результат тренировки:** участник умеет найти задачу, создать ветку, отправить код, пройти ревью и завершить задачу. Для QA и PM допускается тренировочный PR с документацией вместо кода.

## 15. Словарь терминов

| Термин | Простое объяснение |
|---|---|
| **MVP** | Минимальная рабочая версия продукта, которую можно продемонстрировать. |
| **Backlog** | Список идей и еще не подготовленных задач. |
| **Assignee** | Участник, ответственный за Issue. |
| **Acceptance criteria** | Проверяемые условия, по которым понимаем, что задача сделана. |

| **Branch** | Независимая линия изменений. |
| **PR / Pull Request** | Запрос на проверку и объединение изменений. |
| **Review** | Проверка изменений другим участником. |
